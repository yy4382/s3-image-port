## Evidence frame

- Jotai implementation base: `88bda7e` (`codex/deepen-image-storage`).
- Rejected mixed refactor evidence: `2664318` (`codex/upload-pages-xstate-refactor`), including its parent `72d9848`. Code at this ref is evidence, not authority.
- Ordinary user-visible behavior oracle: `72e942667f2fe31b047dae663e4f5484964983c4` (`main`).
- Intentional changes: the supplied handoff at `/private/tmp/s3-port-jotai-reapply-handoff.md`, especially its eight explicit overrides.

The inventory deliberately does **not** choose the final settings or image-catalog module design.

## 1. Authoritative behavior and domain decisions

### Domain/source-of-truth decisions

These decisions are independent of the rejected state-library migration:

1. A settings profile is locally authoritative and persisted under `s3ip:profiles-list`, retaining the current versioned envelope, migrations, defaults, profile ordering, active-index behavior, import/export behavior, and sync-format payload. Base evidence: `88bda7e:apps/web/src/stores/atoms/settings.ts`, `atomWithStorageMigration.ts`, and their tests.
2. The cloud bucket is authoritative for stored images. The image catalog is the active settings profile's local projection; `s3ip:gallery:photos` is only a recoverable `StoredImage[]` cache. The upload queue is in-memory working state. Natural image sizes are a separate persisted local cache.
3. ADR-0001 remains authoritative: the upload queue and per-file pending-upload lifecycles are genuine XState workflows. Existing settings, gallery, sync, and natural-size Jotai state are not made into actors merely for uniformity.
4. React renders reactive state and invokes focused writes/commands. It does not parse settings for command execution, build storage adapters for catalog workflows, merge listings, reconcile confirmed mutations, coordinate profile resets, or own remote-refresh policy.
5. Storage operations read the latest validated settings when the command starts. Invalid settings yield a typed no-IO outcome: no adapter construction and no remote operation. Catalog, upload, storage access, probe, and download share the existing focused `createStorage` seam, not a generic dependency-injection container.
6. The image catalog has one projection authority. A workflow and writable photo atoms must not both own or dual-write the stored-image projection.
7. The catalog cache keeps the existing key and `StoredImage[]` payload. It distinguishes “never loaded” from “known empty,” tolerates malformed data, and treats cache write failure as diagnostic rather than rolling back accepted in-memory facts. The excluded uppercase `Photo[]` migration remains excluded.
8. Refresh has one lifecycle per profile generation: concurrent intents join, foreground can upgrade a background waiter, last-good images remain visible on failure, background success stays silent, failures remain observable, and no automatic retry loop is added. Eligibility changes may schedule one background refresh; render churn and unrelated settings/view/selection changes may not issue lists.
9. Confirmed upload/delete/rename facts update the visible projection immediately and reconcile with overlapping listings so older lists cannot undo them. Key reservations permit disjoint mutations and reject overlapping keys with zero additional IO. Command IDs join only identical canonical commands.
10. Profile generation plus relevant settings/target revision guards async completion. Old work cannot mutate a replacement profile. Semantic storage-target identity is `endpoint + bucket + includePath`; credential, region, `forcePathStyle`, and public-URL changes do not alone change the target.
11. Gallery URL state contains normalized search, prefix/date filters, sort, and page size. Selection and current page stay outside the URL. Direct load and external back/forward hydrate once; one semantic user edit navigates at most once; normalization uses replace; modal return restores the captured gallery URL state.
12. Selection is keyed. Toggling one stored image must not rerender every tile. Derived catalog views and command identities remain stable across unrelated request/status/selection changes.
13. Storage access testing preserves `idle`, `testing`, `success`, `failed`, and `cors-incomplete`, validates current raw settings at invocation, performs no IO when invalid, rejects stale completion after a storage revision change, and ignores completion after disposal.
14. The natural-size cache retains its current key/payload, LRU behavior, malformed-data fallback, debounced persistence, and one clear on profile replacement. The behavior is authoritative; the transition actor at `2664318` is not.
15. The existing sync workflow/UI remains intact. It consumes a stable sync-format projection and applies pulled profiles through the same profile-replacement semantics; it is not redesigned as a machine in this effort.
16. Deterministic injected-adapter tests are the primary race evidence. Selector/atom identity, bounded renders, StrictMode settling, route echoes, adapter/operation call counts, cache failure, invalid-settings no-IO, stale completion, reservations, and both completion orders are required checks.
17. The native-button default for the animated Base UI switch and the gallery measurement cleanup are independent fixes to reproduce. Evidence: `2664318:apps/web/src/components/animate-ui/primitives/base/switch.tsx` and `apps/web/src/modules/gallery/GalleryContent/PhotoGrid.tsx:37-59`.
18. `.pnpm-store` ignoring from independent commit `16264d5` is housekeeping, not state architecture.

### Eight intentional overrides of `main`/the base

These are the only broad user-visible deviations presumed accepted without another HITL decision:

1. Ordinary storage-field edits no longer clear or automatically relist the image catalog.
2. A valid-to-valid storage-target change keeps last-good thumbnails visible but blocks old-target probe/load/copy/download/delete/rename IO until an explicit successful refresh binds the projection to the new target.
3. Successful upload appears immediately in the image catalog, survives upload-route unmount, and rejects a stale completion.
4. Concurrent refresh intents make one list call; route synchronization makes at most one navigation per semantic change.
5. Older listings cannot resurrect or remove confirmed upload/delete/rename results.
6. Overlapping mutations are blocked while disjoint mutations may run concurrently.
7. Upload edit controls close and become inert during processing/uploading; impossible edit events are rejected by the machine as well as disabled in UI.
8. Genuine active-profile replacement clears catalog projection/view/selection, the unkeyed catalog cache, and natural-size cache exactly once; ordinary edits do not.

## 4. Migration-only implementation to discard

Do not port or imitate the following from `2664318`:

1. `@xstate/store` / `@xstate/store-react` dependencies and all code whose purpose is replacing Jotai.
2. Deletion of `jotai`, `jotai-optics`, `Provider as JotaiProvider`, or `atomWithStorageMigration`.
3. `modules/settings/settings-store.ts`, `settings-context.tsx`, and the large `settings/index.ts` export barrel as an implementation. It front-loads dozens of standalone types and exposes far more than five same-purpose interaction points.
4. `modules/app-state/app-state-runtime.ts` and `AppStateProvider.tsx` as an implementation. `AppStateRuntime` exposes settings, catalog, natural-size, sync, upload, getters, factories, commands, probe/download, and four lifecycle methods (`app-state-runtime.ts:66-88`): the exact grab-bag interface prohibited by the standing constraint.
5. `modules/image-catalog/image-catalog-machine.ts` wholesale. It combines a 1,789-line machine, public view commands, runtime commands, cache policy, projection, mutation registries, storage IO, lifecycle, and derivations. Its mutation region is representational while core scheduling/joining lives in closure maps (`:389-445`), so passing machine tests does not establish a coherent reactive owner.
6. `image-catalog-selectors.ts` and `image-catalog/index.ts` as APIs. They expose many same-purpose selectors and retain global per-key/per-operation selector maps (`selectors.ts:70-82,174-244`) without eviction.
7. `image-catalog-context.tsx`'s provider/facade layering and the actor-specific `image-catalog.tsx` test harness.
8. The `fromTransition` sync store in `settings/sync/sync-store.tsx`; retain the base sync atoms/workflow.
9. `natural-size-cache-store.tsx`'s transition actor, global default actor, version counter, and actor provider. Retain behavior through Jotai/plain cache code.
10. Any compatibility facade, event translation layer, shadow catalog, dual writer, generic runtime container, or family of thin command hooks introduced only to bridge old and new state ownership.
11. ADR-0002's proposed global XState destination, the XState rewrite PRD, and `tickets.md` as architecture authority. They are historical evidence. A replacement ADR must supersede ADR-0002 without rewriting history.

Do not cherry-pick `72d9848` or `2664318`; both mix reusable rules/tests with the rejected migration.

## 6. Reactivity risks and regressions

Confidence labels distinguish an observed code delta from an inferred risk.

### High confidence

1. **Missed probe update in the rejected refactor.** At the base, `PhotoDisplayError`'s probe callback/effect depends on both `s3Key` and reactive `s3Settings` (`88bda7e:PhotoItem.tsx:118-134`), so a mounted error tile reprobes when validated settings change. At `2664318`, `usePhotoProbe` depends only on `[key, runtime]`, and `runtime` is stable (`use-photo-probe.ts:5-24`). `runtime.probeStoredImage` reads the latest settings only when invoked; it does not subscribe. Therefore credential/target revision changes while the error UI remains mounted do not trigger a new probe. `use-photo-probe.test.tsx` covers StrictMode dedupe only, not this transition. Whether automatic reprobe is desired must be resolved HITL, but the reactive behavior was unquestionably removed.
2. **Excess selection rerenders at the base.** Every tile reads the whole `selectedPhotosAtom` Set and derives `.has(photo.key)` (`88bda7e:PhotoItem.tsx:48-51`), so any key toggle notifies every tile. `2664318:PhotoItem.selection.test.tsx:75-121` provides a useful contract proving keyed locality, but its selector-map implementation should be discarded.
3. **Ordinary storage edits can drive excess listing at the base.** The form marks the gallery dirty on every S3 form change (`88bda7e:settings/s3/s3.tsx:34-38`); the Gallery effect lists whenever dirty (`Gallery.tsx:15-38`); and `fetchPhotoList` identity follows validated settings (`use-photo-list.ts:105-167`). This directly conflicts with override 1. The fix must preserve the remaining Jotai subscriptions while proving zero lists for ordinary edits.
4. **Upload route lifetime loss at the base.** `Upload` owns `UploadQueueProvider` inside the route component (`88bda7e:upload/upload.tsx:27-36`), so route unmount destroys the queue. `2664318:AppStateProvider.test.tsx:178-254` confirms the desired survival behavior, but not the runtime design.
5. **Duplicate subscription in rejected upload UI.** `2664318:FilePreview.tsx` both calls `useSelector(uploadActor, selectCanEditPendingUpload)` and installs a manual `uploadActor.subscribe` solely to close the editor (`:54-70`). This creates two reactive paths for the same fact and extra update/cleanup surface. The editor-lock tests prove behavior, not the necessity of both subscriptions.
6. **Unbounded selector identity registries in rejected catalog API.** `image-catalog-selectors.ts` stores selector closures in module-global Maps for every selected key, busy key, and operation ID, with no eviction (`:70-82,174-244`). This is concrete retained state outside the actor and a direct consequence of the many-selector facade. Do not port it; keyed Jotai subscriptions need an explicit lifetime policy.
7. **Broad interface/type-first migration is itself unsafe evidence.** `settings-store.ts` declares a large type/API inventory before implementation (`:44-236`), `image-catalog-machine.ts` does the same (`:41-394`), and `AppStateRuntime` has more than ten interaction points. This violates the standing inference-first/deep-interface constraints even where individual tests pass.

### Medium confidence / requires targeted verification

1. **Route echo and missed interleaving risk.** The base has two mutually corrective effects with deep-equality refs (`88bda7e:DisplayControl.tsx:38-78`). The rejected replacement still uses one large effect with three mutable coordination refs and many semantic/object dependencies (`2664318:use-gallery-route-sync.ts:22-112`). Its tests cover direct load, one outward edit, and serial back/forward under StrictMode, but not rapid user edit interleaved with external navigation, two external changes before outbound settlement, or equivalent objects with different key order. Port the contracts, not this effect.
2. **Frozen provider inputs can miss rebinding.** `2664318:AppStateProvider.tsx:29-32` snapshots `input` once, and nested settings/upload/natural-size providers similarly create one instance with `useState`. This is acceptable only if “input never changes for a provider lifetime” is an explicit contract. Tests cover isolation and unmount, not prop replacement.
3. **Post-commit hydration can produce transient/default reactive reads.** The rejected provider constructs deferred modules with default state during render and hydrates them in `useLayoutEffect` activation (`AppStateProvider.tsx:29-56`, `settings-store.ts:244-310`, catalog `:403-427,1457-1481`). Tests prove storage is not touched before commit and that actors settle, but do not characterize every settings form/gallery consumer's intermediate render or controlled-form synchronization. The Jotai base's storage atoms already have established hydration semantics and should remain the oracle.
4. **Broad settings subscription creates excess cross-module work.** `app-state-runtime.ts:195-205` observes every settings snapshot, calls target observation, and recomputes background eligibility. Guards prevent some IO, and one test proves one valid-to-valid edit does not list, but render/emission counts across rapid raw-invalid edits, access-test status changes, upload/gallery changes, and sync metadata changes are not covered.
5. **External form replacement is under-tested.** `S3SettingsTsForm` passes a reactive settings projection as `useAppForm` `defaultValues` at both base and refactor, but `2664318:s3.test.tsx` tests only user-originated edits, not an active-profile/sync replacement while the form remains mounted. This may be a pre-existing issue rather than a migration regression; it needs a characterization test before touching the form/effect.
6. **Closure-owned workflow state is invisible to React snapshots.** The rejected catalog keeps active refresh, operation, command, and reconciliation registries in closures (`image-catalog-machine.ts:389-445`) while React subscribes to an actor context. Tests cover many terminal outcomes but not every intermediate consistency relation between registries and snapshot state. This is another reason to port rules/tests, not the machine.
7. **Sync transition actor can perform excess persistence.** `sync-store.tsx:123-129` writes both config and token on activation and on every active snapshot, even if only one value changed or a structurally equal event was sent. This does not establish a user-visible regression, but it is concrete excess local IO absent a semantic no-op guard.

### Coverage limitations

- No live credentialed S3 list/upload/delete/rename/access smoke was run for `2664318`; `tickets.md` explicitly reports deterministic adapters only.
- Passing `2664318` tests prove the tested actor/store implementation under its harness, not Jotai 2 + XState 5 + React 19 `jotai-xstate` lifecycle compatibility.
- There is no exhaustive render-count matrix for all settings fields, catalog statuses, route transitions, selection changes, upload child transitions, and natural-size updates.
- The refactor replaced/deleted broad main/base UI test files (notably profile and granular S3 tests) with smaller consolidated suites. Keep the oracle tests; do not treat refactor test count as behavior equivalence.
- This investigation was static/read-only; no production or test suite was executed because the ticket requested evidence gathering and docs validation only.

## Guardrails carried forward

- TypeScript remains JavaScript-like and inference-first. Core data types come from Zod schemas. Explicit types are reserved for real seams/outcomes, not declared in bulk before code.
- Prefer one deep module/object with high leverage. Do not create thin pass-through wrappers, selector barrels, command-hook families, generic runtime containers, or more than five similar same-purpose interaction points.
- Do not massively edit Jotai atoms, Jotai optics, providers, `useEffect` paths, or other React reactivity. Every touched reactive path needs a named behavioral reason plus missed-update, excess-update/loop, identity, render-bound, and IO-count evidence proportional to the risk.
